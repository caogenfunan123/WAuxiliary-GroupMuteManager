# 03 · 踩坑记录（走过的全部错路）

按`现象 → 假设 → 实验 → 证伪 → 真根因`记录。**每条错路都有当时的日志证据**（脱敏版见 `logs/`）。

---

## 坑 1：T / SP 极性写反

- **现象**：插件开了静音，群聊信息页开关显示"关"，列表图标时有时无
- **错路**：凭 UI 反推，认为静音对应 `T=1`、`SP room_msg_notify=false`
- **证伪**：读 `RoomInfoDetailUI.X6` 源码——`this.g = z3VarN.T; g==0` → 标题静音图标可见、checkbox 选中、SP=true；点击 handler `g = 1-g`
- **修正**：`J2(mute ? 0 : 1)`，SP 写 `mute` 本身

## 坑 2：BeanShell/ART 的 `byte[]` 反射陷阱（本项目最大的暗礁）

- **现象**：`method X argument 1 has type byte[], got java.lang.Object[]`
- **触发**：把 `byte[]` 作为 `new Object[]{...}` 的一个元素传给反射 `invoke/newInstance`
- **诡异点**：同代码在 PC 上用独立 bsh 2.0b6 + JVM 跑 **4 项全过**（见 `tests/bshtest*.bsh`），设备上全炸 → 判定为 **ART + WAux bsh fork 特有**，不是语法问题
- **影响面**：`protobuf.f.parseFrom(byte[])`、`protobuf.g.<init>(byte[])`、`r45.cu5.<init>(byte[])` 全部不能直接用
- **绕过**（本项目所有字节构造都靠这条）：
  ```java
  // bytes → latin1 String → 微信自带工厂还原，全程零 byte[] 参数
  StringBuffer sb = new StringBuffer(len);
  for (int i = 0; i < len; i++) sb.append((char)(bytes[i] & 0xFF));
  Object g = com.tencent.mm.protobuf.g.a(sb.toString(), "ISO-8859-1");
  // g.a(String,String) = new g(); g.a = data.getBytes(charset)
  ```
- **附带教训**：能传 proto 对象/int/String 就绝不传裸数组

## 坑 3：`xg3.p0` 构造器签名——具体类型找不到

- **现象**：`NoSuchMethodException: xg3.p0.<init> [int, r45.tn4]`
- **错路**：以为 ctor 吃具体 proto 类型
- **真签名**：`xg3.p0.<init>(I, Lcom/tencent/mm/protobuf/f;)V` —— 吃的是**基类** `protobuf.f`
- **教训**：反射 ctor 参数一律按 smali 的声明类型找，别按调用处的具体类型猜

## 坑 4：队列层级——`e21.g` 不是 NetScene

- **现象**：`method r1.h argument 1 has type com.tencent.mm.modelbase.m1, got e21.g`
- **链路**：`gm0.j1.d()` → `modelbase.r1`；`r1.g(m1)=h(m1,0)` 收的是 **`m1`（NetSceneBase）**
- **辨析**：`e21.g` extends `k1`（= `MicroMsg.MMReqRespBase`），不是 `m1`；真正的 NetSceneOplog 是 **`e21.j`**（extends `m1`）
- **`e21.j` 的正确用法**：`new e21.j(List<xg3.q0>)`，构造器内部 `new e21.g(); ((e21.h)e.getReqObj()).a.d = H(ops)`，其中 `H(List)` 把每个 `xg3.q0` 转成 `r45.b50{d=cmdId, e=cu5{d=len, f=g}}` 塞进 `r45.c50{d=count, e=LinkedList}`
- **结局**：按此构造后 `入队=true`，但 mute 仍在 2 分钟内被冲掉 → 问题不在层级，在**命令**（坑 5）

## 坑 5：RunCgi 直发也没用——命令根本错了

- **尝试**：WeKit `sendCgiRaw` 同款路径：`r45.l` builder(a=h25,b=i25,c=uri,d=681) → `a()` 得 `modelbase.o` → `modelbase.z2.d(o, null, false)`（RunCgi，自带 HandlerThread，`scene=modelbase.c3` 返回成功）
- **结局**：同样 2 分钟内被冲掉
- **结论**：层级/队列/dispatcher 全都通了，但**cmd 2（modContact）不是通知开关的认账通道**
- **正解**：回到原生 UI handler，挖出 `mn.a(roomId, g, 0)`：
  - `mn.a extends xg3.q0`，ctor `(String,int,int)`，`super(0x14)` → **cmd 20**
  - 载荷 `new r45.rn4{du5.d=username, e=g, f=0}`
  - `fj().c(task)` 压任务队列，无 callback
- **实测**：v2.9.4 起补 cmd20 → 用户连切多个群不再回弹

## 坑 6（方法论）：注入上下文里"入队"≠"送达"

- WeKit 源码原话：WeNetSceneQueue "doesn't reliably flush from an injected context"
- 本项目三次独立复证：`fj().c(p0)` 入队 null、`r1.g(e21.j)` 入队 true、`z2.d` 返回 c3——**链路指标全绿，服务端全没收到**
- **教训**：在 Xposed/注入环境里，"队列接受了我的 scene" 不能作为送达证据；唯一的送达证据是**最终业务状态是否存活**（对照实验 + 状态回读）
