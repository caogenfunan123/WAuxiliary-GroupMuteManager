# 05 · 验证方法（全程不让用户动手）

用户约束：**不许让使用者跑手动步骤、转述截图**。所有验证都由 Agent 自主完成，手段如下。

## 手段清单

| 手段 | 用途 | 命令/位置 |
|---|---|---|
| **插件自检线程** | 重启后 6s 自动执行一次真写，日志回读状态 | `main.java` 的 `new Thread(...sleep 6000...)` |
| **幂等目标态** | 自检写成"固定目标态"（mute=true），重复执行不翻转、可反复对照 | `_gmSetMute(room, true)` + 前后各读一次 |
| **重启循环** | 模块只在微信启动时读插件 → 部署后重载 | `am force-stop com.tencent.mm; sleep 4; am start -n com.tencent.mm/.ui.LauncherUI` |
| **退后台逼同步** | 制造一次服务端/缓存同步，观察本地是否被冲 | `input keyevent 3; sleep 45-60; am start ...LauncherUI` |
| **飞行模式对照** | 区分"服务端冲掉"还是"本地重置" | `cmd connectivity airplane-mode enable/disable` |
| **日志 grep** | 所有断言以 plugin.log 行为证 | `/storage/.../Plugin/群免打扰管家/plugin.log` |
| **盲点 UI**（辅助） | 会话列表点第一行/输入框盲打 | `input tap x y`（uiautomator 在 secure window 不可用） |
| **DB 行 DUMP** | 诊断时打印 rcontact/rconversation 整行 | `_gmDumpRow`（`db.f("select * from ...", null, 2)` 游标直读，无需解密 SQLCipher） |

## 自检日志的关键行（成功态）

```

type/T持久化 ... T=0 结果=1
cmd20任务 5364****@chatroom mute=true g=0 入队=null     ← 入队 null = fj().c 的 void 返回，正常
写入 ... mute=true 原生=true type回读=515 生效=true      ← 515 = 512|2|1 = 静音位在
```

## 证伪一个假设的最小实验

每个根因都靠"做一个只改一个变量的对照"定案：

1. **极性**：读 `X6` 源码 → 对比写入前后 T/SP 实际值
2. **byte[] 陷阱**：PC bsh 2.0b6 跑4项对照（`tests/`）→ 同代码设备全炸 → 锁定 ART/WAux 特有
3. **送达**：bg/fg + 重启后状态回读；离线（飞行模式）重复同实验
4. **命令**：cmd2（队列/RunCgi 两姿势）vs cmd20（`fj().c`）同环境对比，只有 cmd20 存活

## 部署流程（每次迭代）

```bash
# 1) 工作区改代码 → root_deploy 推到插件目录
# 2) 重载
am force-stop com.tencent.mm; sleep 4; am start -n com.tencent.mm/.ui.LauncherUI
# 3) 读自检日志
grep -E "自检|cmd20|写入" <pluginDir>/plugin.log | tail -5
```

## 已知取证死角

- WeChat 主 xlog（`MM.mmap3`）定制 zstd 封装，strings/裸解压均失败 → 未采用
- `uiautomator dump` 对 WeChat secure window 恒定失败 → UI 状态全部靠运行时 API 回读
- SQLCipher 加密的 `EnMicroMsg.db` 不直接读 → 走 `db.f()` 运行时查询或 API
