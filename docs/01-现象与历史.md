# 01 · 现象与历史（用户原话时间线）

按用户反馈的原话顺序还原，这是整个排查的主线。每一句抱怨都对应一个被修正的根因。

### 阶段 1 —— "闪一下就恢复"
> 「设置免打扰 闪了一下免打扰图标就又恢复了 没有成功免打扰」

初版插件直接照抄 WeKit（第三方）的做法：调 `c01.e2.p0/z0` 原生 setter + `Bi().p0` 落库。图标闪出 = 本地 type512 写上了，随即被抹平。
**根因**：只写了本地，没发服务端 oplog；一段时间后服务端同步回来覆盖。

### 阶段 2 —— "长按那个能开关，设置里面不能开关"
> 「有一个版本都成功一半了 我提示过你 长按那个能开关，设置里面不能开关 越修越垃圾」

用户点破关键：微信自带的群聊信息页开关能用，插件写的开关图标在、行为不在。
深入 `RoomInfoDetailUI.X6` 后发现它根本**不读写 type512**：它只维护 `this.g`（= `z3.T` 缓存字段）和 SP `room_msg_notify`，而 `T` 不是 DB 列，只在 ContactStorage 的 `s` 构造器里 `this.T=1` 初始化。
**根因 1（极性反了）**：插件写 `T` 和 SP 时极性写反——静音时写 `J2(1)` + `SP=false`，原生页面读出来直接判定"未静音"。
**根因 2**：`T` 靠缓存回填（`k4.n(roomId,true)` 命中 `this.i` map 才保留），缓存被服务端同步替换就归 `1`，所以设置页闪回。

### 阶段 3 —— "保持不了一点"
> 「保持不了一点 切换了过一会又切换回去了 你继续深挖反编译微信看看」

本地三路（type512/T/SP）全写对后仍回弹。对照实验确认：飞行模式下也回弹 → 排除纯服务端拉取，锁定"oplog 从未真正送达"。
先后尝试了四条直发链路，全部死在不同环节（见 `03-踩坑记录.md`），最终挖到官方 UI handler 的真实动作：`new mn.a(roomId, g, 0)` 压入任务队列。
**根因**：oplog 命令用错——一直在发 **modContact（cmd 2）**，而 UI 原生点击发的是 **cmd 20** notify 任务（`r45.rn4`）。

### 阶段 4 —— 定版
用户实测批量切换多个群不再回弹（2026-09-22 19:27-19:28 日志），v2.9.4 之后进入功能迭代。
